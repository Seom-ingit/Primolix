# 什么时候该用它，什么时候不该

*English: [when_to_use.en.md](when_to_use.en.md)*

> 本页只讲取舍。数字都是本机、同一批次的读数（跨批次绝对值会漂 20%–40%，个别批次可达 2 倍），完整口径见 `docs/` 下的研究记录。
> 与其它实现的同批对照见 `docs/`，本页不做倍数断言。

## 它是什么取向的东西

`primolix` 是"索引生命周期"取向的稀疏检索内核：写入、改参数、解释、对账都便宜，
代价是每次查询现算分数。所以它和"把算好的权重预先存好"的方案是一个反过来的取舍：

| | 预计算加权分数 | primolix |
|---|---|---|
| 查询 | 快（读现成数） | 默认现算（44,757 篇文档上 **0.049 ms/查询**，快速路径默认已开）；开可选物化层后可反超：50 万篇 **1.16 ms**，同批预加权方案 **1.39 ms** |
| 改文档 | 贵（通常整库重建） | 便宜：0.22 µs/token，改 100 篇只做那 100 篇 |
| 改参数 | 贵（重建） | 便宜：`k1`/`b` 是 1.2 µs；换 idf 是 5.3 ms |
| 解释排序 | 只有一个总分 | 可按词拆解，且逐位自洽 |
| 改完确认 | 重建后对账 | 只核对原语，8.7 ms，与改动量成正比 |

## 该选它（有几个就值得考虑）

- **文档经常增删改**：增量写入是真增量（墓碑 ＋ 尾部追加），不动其余文档。
- **要反复调参、做 A-B**：改 `k1`/`b` 不动物料、不重建；两个视图可以同时开着比。
- **要解释"为什么这篇排前面"**：分数可按词拆成 idf × 饱和项 × 文档长度。
- **要审计、对账**：改动后只核对原语（`df`/`dl`/墓碑）就能确认结果，成本与改动量成正比。
- **要回滚、多版本**：视图是"段清单 ＋ 墓碑 ＋ 参数 ＋ 词表代次"，切视图只换清单（本机约 10.9 ms）。
- **纯 CPU、依赖要轻**：核心只依赖 numpy ＋ scipy，不需要 GPU；常驻私有内存 2.80 MB（小索引实测）。
- **要在同一份索引上继续压延迟**：默认路径已经把"白拿"的优化开满了；要不要再开物化层 `W_CACHE`
  （用内存换延迟）或多进程共享 `TC_SHARED`（用部署形态换常驻），见 README 的「性能开关」一节与
  [`api.md`](api.md) 的"开关怎么选"。
- **长期只追加**：块数增长会拖慢查询，压实 21 ms，约 130 次查询回本。

## 别选它（有任意一条，先看别的方案）

- **只读、永不改动、且不开物化层**：那就没有"省下来的重建"可赚，预计算方案（或现成的倒排库）更省查询延迟。
  这是它最不划算的场景 —— 但开了物化层 `W_CACHE` 之后，同批读数里物化层反超（**1.16 ms** 对 **1.39 ms**）。
- **单次查询延迟是硬指标**（例如 P99 卡得很紧）：每个查询都在算分，比"读现成数"慢。
- **要多模态**（图像 / 音频 / 视频）：本包只处理文本 token。
- **要分布式、多机分片的「开箱即用」**：本包是单机单索引，没有分片路由与协调层 ——
  这是「未实现」，不是机制劣势。三件不同的事要分开：
  ① **低常驻私有内存是优势**（内存受限时，每机能放更多分片或副本；索引段只读、天然可复制，
     视图就是"段清单 ＋ 墓碑 ＋ 参数 ＋ 词表代次"）；
  ② **但"低内存换每核吞吐更大"不成立** —— 查询是 CPU 现算，瓶颈通常在 CPU 而非内存；
     低内存带来的是部署密度，不是每核吞吐；
  ③ 分片真正的难点是全局 `idf`（依赖全局 `df`）。而这恰好是"把 `df` 当原语存"能精确解决的：
     汇总全局 `df` 即可算精确 idf，不必重建各分片（预计算加权分数的方案则必须重建）——
     所以在这两点上，这套设计反而是占优的一方。
- **要 GPU 加速的稠密检索**：核心是 CPU 稀疏；`dense` 只是可选的候选精排 extra。
- **新词会频繁出现**：内核词表封闭。表外词不会被静默丢掉：`update()` 会整库回退重建，并返回
  `kind='rebuild'`（词表内改动才走增量，返回 `kind='incremental'`）。所以这条不是"不能用"，
  而是"改动里有连续新词时，你会反复付整库重建的钱"—— 如果这是常态，先解决词表来源
  （把新词并入建库侧），或改用词表开放的方案。
  另一条路线已接进内核（最小档）：`SparseBM25.mount_segment(...)` 把新词放进只读段接住
  （段带原语，打分用合并 `df`，`segment_report()` 给出词表代次），与全库重建逐位一致
  （实测 `max|Δ| = 0`），不动主表 `T`、不写盘；`fold_segment(tag)` 可再把段并进主表
  （折叠前后分数不变），`unmount_segment(tag)` 可把已挂的段逐项撤回（**后进先出**，且仅对未折叠段）。
  代价是查询随段数增长（实测次线性：30 段约 5 倍）。**并发换段：已实测不是原子的** ——
  无锁时约 **3%**（多次实测 2.3%–3.7%）的并发读数撕裂（其中 **96% 是静默错分**）；**内核默认已加可重入读写锁**
  （`SWAP_LOCK=True`：读者并发、写者独占；实测 **0 撕裂**，代价约 **+3.4 µs/查询**），
  门面层再加一层更粗的锁让跨调用组合原子；单线程可关 `SWAP_LOCK` 拿回开销
  （出处：`research/fold_demo_probe.py`，该台子未随本发布包提供；读数见 `research/oov_segment2_probe.json`
  与 `research/segcount_probe.json`，同样未随本发布包提供）。
- **规模远超已验证范围**：本包发布的绝对数取自 4.5 万文档规模；50 万篇与 100 万篇的读数只在同一批次内可比较。
  上一代系统有 8.84M 篇的实测，那不是本包的读数。
- **不要手动删索引里的任何文件**（见 `docs/index_format.md` 的实测表）；要清理就整目录删掉重建。

## 对比的定位（类别级）

- **对"预计算加权分数"类方案**：当改动频繁时选 primolix；当只读且查询密集时选它们。
- **对"成熟倒排索引库"**：当需要生态、插件、分布式、多年打磨的运维面时选它们；
  当需要原语可逆、真增量、可归因时选 primolix。两者也可以并用（各管一段）。
- **对"向量库 / 稠密检索"**：解决的是语义互补问题，不是替代关系；
  本包可以当它们的粗筛（`dense` extra 就是按这个思路留的）。

## 三个问题定结论

1. **这个语料会变吗？**
   不会 → 优先预计算方案。会 → 继续。
2. **你要不要"改完立刻能查、改参数不重建、能解释排序"？**
   不要 → 预计算方案更省。要 → primolix。
3. **你的延迟预算能不能接受"查询期现算"？**
   不能（P99 极紧）→ 用 primolix 做写入与对账，另配一个预计算或向量索引做线上查询。
